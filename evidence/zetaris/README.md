# Zetaris evidence pack

This folder is the artefact bundle a judge can inspect to see Zetaris doing real work in this project. Every file is captured against the local Zetaris install (`zetaris-driver-1` at `http://localhost:8888/api/v1.0`) through the committed adapter and bootstrap scripts.

| file | what it is | regenerate command |
|---|---|---|
| [`usl-ddl.sql`](usl-ddl.sql) | The `COMPILE USL` DDL the bootstrap script sends to Zetaris. Six entity tables with inline primary + foreign keys. | copy-paste from `scripts/zetaris_bootstrap.ts` (`uslSteps()`). |
| [`run-dq.md`](run-dq.md) | Live `RUN DQ TABLE` output across every USL entity, captured on 24 Oct 2026. Rule / table / total / valid / invalid, exactly how Zetaris returns it. | `npx tsx scripts/zetaris_bootstrap.ts --apply` or the one-off runner at `evidence/zetaris/run-dq.ts` (included below). |
| [`bootstrap.txt`](../zetaris-bootstrap.txt) | The 39-step idempotent bootstrap trace from the last fresh install. | `npm run bootstrap:zetaris -- --apply`. |

The adapter path (packages/adapters/src/zetaris.ts) is the only module that talks to Zetaris in product code. Nothing in this folder is generated by a model; every number is a Zetaris REST response.

## Scope

- The bootstrap registers four data sources with their native Zetaris verbs: `CREATE DATASOURCE` for the Postgres JDBC source, `CREATE REST TABLE` + `CACHE TABLE` for the three MAILGW endpoints, `CREATE FILESTORE TABLE` for the asset + Turkish-phishing CSVs, and a REST + CACHE pair for the public CISA KEV JSON.
- `COMPILE USL IF NOT EXISTS security_usl DEPLOY NAMESPACE lightning.metastore.whytrace DDL …` builds the unified semantic layer; each `ACTIVATE USL TABLE` wires an entity to its source projection.
- `RUN DQ TABLE` is applied to every entity. The returned rows carry Zetaris's `type` ("Primary Key Constraint" / "Foreign Key Constraint") and `total_record` / `valid_record` / `invalid_record` counts. Custom DQ checks (`valid_upn`, `ts_not_null`, `known_result`, `vpn_session_order`, `asset_seen_recent`) live in `packages/agents/src/dq.ts` and run alongside this at investigation time.

## Zetaris lessons for other builders

Things the bootstrap hit on the local install (OSS driver + API) that cost real time and that another builder would hit the same way. Lessons we *actually* ran into — not guesses:

1. **File store ingest = `docker cp`.** The local image has no upload endpoint; the only reliable way to seed `FILES` tables was `docker cp *.csv zetaris-driver-1:/home/zetaris/customer-data/shared/whytrace/`. The script does this before `CREATE FILESTORE TABLE`. An upload endpoint in the UI or API would turn these two steps into one.
2. **DDL is not fully idempotent.** `CREATE SCHEMASTORE CONTAINER` has no `IF NOT EXISTS`, and several `DROP` forms are not supported. The bootstrap uses `tolerate: () => true` on the "already exists" branch so a re-run is safe. Adding `IF NOT EXISTS` + `OR REPLACE` to the DDL surface would remove this error-string handling.
3. **Custom DQ rules are not first-class.** `REGISTER DQ` did not accept our custom rule DDL, and `SHOW DQ RULES` is not supported on this version. Our custom checks live in application code (`packages/agents/src/dq.ts`) and run next to `RUN DQ TABLE`. First-class `REGISTER DQ` + a listing verb would close this gap.
4. **Typed JSON results, please.** The REST API returns every value as a string ("142" / "false" / "2026-10-14T06:12:00Z"); the adapter has a `typeRows()` casting pass that converts strings to numbers / booleans / timestamps using the column's `headers[]` type hints. A typed JSON response (or a column-type block in the response envelope) would delete that pass.
5. **No cursor paging; `limit` is the whole story.** `signins_for` caps at `DEFAULT_LIMIT=200` because that is the ceiling the REST API supports per call. Cursor paging would let the Investigator fetch > 200 rows without stitching multiple `limit`-offset queries.
6. **`UNCACHE TABLE` + `CACHE TABLE` is the refresh.** For REST-backed MAILGW tables that cache on first query, a schema or data refresh requires `UNCACHE TABLE … ; CACHE TABLE …`. The eval harness does this before every blind set run so mail-event rows reflect the current fixtures.
7. **JSON arrays, not JSON Lines.** The REST source definition expects a JSON array response body for a REST table, not newline-delimited JSON. The MAILGW mock service was updated to return `[{…}, {…}]` instead of `{"records":[…]}` or NDJSON after the first `CACHE TABLE` returned zero rows.
8. **Least-privilege keys are a day-2 story.** A Zetaris API key carries all rights of its user. For a production deployment a view-only agent key is possible but requires per-namespace + per-model `SELECT` ticks in the UI (see the "Least-privilege agent key" section of the top-level README). The demo install uses the admin key.
9. **`REMOVE USL … NAMESPACE …` before `COMPILE USL IF NOT EXISTS`.** On the local install, re-running `COMPILE USL IF NOT EXISTS` without first `REMOVE USL`-ing stayed on the old namespace. The bootstrap now does `REMOVE USL security_usl NAMESPACE lightning.metastore.whytrace` with `tolerate` before every compile.
10. **CISA KEV updates fast; cache it.** The `KEV` database is a public REST endpoint; `CACHE TABLE` is what makes the bootstrap finish in ~18 s instead of hitting the public API on every `kev_exposure` query. The idempotent bootstrap takes ~7 s of its wall-clock on that single download.

These lessons are also summarised in the top-level README section "How Zetaris could improve"; the version here is the longer, builder-oriented list.
